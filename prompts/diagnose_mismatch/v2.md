A Qlik table was translated to Dremio SQL, statement by statement, and run against its evidence (reload-log row
counts, QVD field aggregates). Some comparisons failed. Find the statement whose SQL does not reproduce Qlik, and
give replacement SQL for that one statement.

You receive, for the table: each statement (`statement` number, Qlik text, its input columns, and the SQL it was
translated to, which reads its input as `src`) and the failed comparisons (check, subject, expected, got). You
never receive data rows; aggregates such as min, max, distinct and sum are enough to locate the difference.

Typical causes: number-to-text conversion (Qlik writes 20, not 20.0, and has no trailing zeros), NULL handling,
case-sensitivity, rounding, date or number formats from the script settings, filters, join keys, fan-out.

Answer:
- "statement": the statement number to replace, or null when no single statement is at fault.
- "sql": the replacement Dremio SELECT for that statement, reading `src` only, returning the same columns with
  the same names (double-quoted), every field of the statement, not only the faulty one.
- "cause": one of fan_out, filter_or_variable, expression_semantics, formatting, data_drift, wrong_source, unknown.
- "explanation": which comparison shows it and why the new SQL fixes it.
Failed comparisons on text columns show formats only, never values (a = a varying word, 9 = a number;
punctuation, spaces and words common to every value are shown as they are).
- SQL string literals are not escaped with backslashes: a regex dot is written '\.' (one backslash), never '\\.'.
Never return SQL identical to an earlier attempt. The replacement is accepted only if every comparison passes when the table is run again; you may be asked again
with the remaining failures.
